# Pit Wall — второй экран для Формулы-1

Веб-приложение «второй экран»: рядом с доступной трансляцией показывает то,
чего нет в обычном эфире — таблицу разрывов (Timing Tower), карту трассы с
машинами в реальном времени, телеметрию выбранного пилота и стратегию шин.
Видео не транслируется (см. ТЗ §1.3) — только публичные данные тайминга и
телеметрии.

Это **каркас целевой архитектуры** из ТЗ, доведённый до рабочего end-to-end:
- **Бэкенд:** FastAPI (Python, async), изолирующий источник данных за адаптером.
- **Фронтенд:** одностраничное приложение на чистом HTML / CSS / JS (Canvas).
- **Хранилище:** PostgreSQL + Redis (через docker-compose), с мягкой деградацией.
- **Данные:** живой OpenF1 **или** встроенный оффлайн-фикстур (одна переменная).

## Быстрый старт

### Вариант 1 — всё в Docker (Postgres + Redis + бэкенд)
```bash
docker compose up --build
# открыть http://localhost:8000
```
По умолчанию источник — `fixture` (встроенная гонка-образец, работает без сети).
Чтобы включить живые данные OpenF1, в `docker-compose.yml` смените
`PITWALL_DATA_SOURCE` на `openf1`.

### Вариант 2 — локально, без инфраструктуры
```bash
cd backend
pip install -r requirements.txt
python scripts/fetch_circuits.py        # контуры трасс (запасная геометрия)
python scripts/generate_fixture.py      # демо-сессия
uvicorn app.main:app --reload
# открыть http://127.0.0.1:8000
```
Оба набора данных — артефакты сборки и в репозитории не хранятся (создаются
автоматически при деплое). Из корня проекта то же самое: `make data`.
Без `PITWALL_DATABASE_URL` / `PITWALL_REDIS_URL` приложение работает на
in-memory кэше и без БД — все эндпоинты доступны.

### Тесты
```bash
cd backend && pip install -r requirements-dev.txt && pytest
```

## Переключение источника данных

Единственная переменная решает, откуда берутся данные (ТЗ §6.4, R-04):

| `PITWALL_DATA_SOURCE` | Поведение |
|---|---|
| `fixture` (по умолч.) | Демо-сессия `session_key=9999`, полностью оффлайн |
| `openf1` | Живой REST OpenF1 (`/sessions`, `/position`, `/car_data`, …) |

Фронтенд и сервисный слой **не меняются** при переключении — это и есть смысл
адаптера источника.

> **Что такое демо-режим.** `fixture` — это *имитация* для работы без сети: полный
> грид сезона-2024 (20 пилотов, реальные номера/команды/цвета) и реальный контур
> трассы, но позиции, круги и телеметрия рассчитаны моделью, а не взяты из архива
> гонки. Настоящие данные гонок — только в режиме `openf1`.

### Откуда берётся геометрия трассы
1. **Основной способ (ТЗ §2.3, метод 1):** контур трассируется по `x,y` из
   `/location` за один *быстрейший* круг сессии. Запрос жёстко ограничен окном
   этого круга — иначе OpenF1 отдал бы всю сессию (~26 000 точек на пилота).
   Результат сглаживается (R-05) и прореживается до 300 точек.
2. **Запасной способ (метод 2):** если `/location` недоступен или точек слишком
   мало, берётся реальный контур из каталога (`scripts/fetch_circuits.py`),
   подобранный по названию трассы/страны.

## Архитектура

```
                    ┌──────────────────────────── backend (FastAPI) ───────────────────────────┐
                    │                                                                            │
Браузер (SPA) ──────┼──▶ api/ (routers)  ──▶  services/  ──▶  sources/ (adapter)  ──▶  OpenF1 / фикстур
  HTML/CSS/Canvas   │      стабильный          нормализация      OpenF1 | Fixture                │
                    │      контракт            + дисциплина §5    (единый интерфейс)              │
                    │           │                   │                                             │
                    │           │                   ├──▶ cache/  (Redis | in-memory LRU)          │
                    │           │                   └──▶ db/     (Postgres | выключено)           │
                    └──────────────────────────────────────────────────────────────────────────┘
```

Слои (каждый — своя ответственность, зависимости идут внутрь):

- **`app/core`** — конфигурация (pydantic-settings) и логирование.
- **`app/domain`** — нормализованные модели (контракт с фронтом), не зависят от
  вендора. Если OpenF1 переименует поле — правится только адаптер.
- **`app/sources`** — `DataSource` (ABC) + `OpenF1Source` и `FixtureSource`.
  Источник изолирован здесь целиком (R-04). Адаптеры отдают «сырые» записи
  формы OpenF1; нормализация — одна, в сервисах.
- **`app/services`** — `normalize.py` (чистые функции raw→domain) и
  `session_service.py` (оркестрация: окна по времени, прореживание,
  телеметрия только для активного пилота, кэш неизменных данных повтора).
- **`app/cache`** — Redis, с автоматическим откатом на in-memory при недоступности.
- **`app/db`** — async SQLAlchemy + Postgres; персистентность **опциональна**
  (без БД приложение работает, просто не сохраняет).
- **`app/api`** — HTTP-роутеры: стабильный, source-agnostic контракт.
- **`app/news`** — каркас подсистемы новостей (ТЗ §10): реестр источников и
  нормализованная схема статьи уже есть; конвейер collect→translate — заглушка (N1).

### Дисциплина загрузки данных (ТЗ §5)
Реализована в `session_service`:
- **DR-01** окна по времени для `/position`, `/intervals`, `/location`;
- **DR-02** прореживание координат карты и точек графика телеметрии;
- **DR-03** подробный `/car_data` тянется **только для активного пилота**;
- **DR-04** неизменные данные повтора кэшируются (Redis/LRU, длинный TTL);
- **DR-05** лимиты OpenF1 — см. ниже.

### Как соблюдаются лимиты OpenF1 (DR-05)
Наивная реализация упирается в рейт-лимит мгновенно: один кадр = 3 запроса к
источнику, а плеер обновляется несколько раз в секунду. Здесь это решено на двух
уровнях:

- **Кэш временных окон.** Запрос к источнику кэшируется по «бакету» времени
  (`frame_bucket_s`, по умолчанию 1 с). Ключ содержит сам интервал, поэтому его
  содержимое неизменно — TTL может быть длинным, а свежесть ограничена размером
  бакета. Десятки обращений внутри одной секунды (и все зрители сразу) дают
  **один** запрос к OpenF1.
- **Темп опроса задаёт сервер.** `/api/health` отдаёт `poll_interval_ms`
  (300 мс для демо, 1500 мс для живого OpenF1). Плавность движения машин при
  редких ответах обеспечивает интерполяция на клиенте, а не частые запросы.

## API (контракт для фронтенда)

| Метод | Назначение |
|---|---|
| `GET /api/health` | статус, источник, backend кэша, включена ли БД |
| `GET /api/sessions` | список гонок для выбора |
| `GET /api/sessions/{sk}` | сведения о сессии (в т.ч. всего кругов) |
| `GET /api/sessions/{sk}/drivers` | пилоты (акроним, номер, команда, цвет) |
| `GET /api/sessions/{sk}/bounds` | временные границы (для скраббера повтора) |
| `GET /api/sessions/{sk}/frame?offset=<с>` | **кадр**: тайминг, позиции машин, флаг, круг, погода |
| `GET /api/sessions/{sk}/track` | геометрия трассы (контур из `/location`, R-05 сглаживание) |
| `GET /api/sessions/{sk}/tyres` | стинты по пилотам |
| `GET /api/sessions/{sk}/telemetry?driver=&offset=&window=` | окно телеметрии активного пилота |
| `GET /api/season?refresh=` | календарь, личный зачёт, кубок конструкторов (Jolpica-F1) |
| `GET /api/news?sources=&limit=&refresh=` | лента новостей (агрегация RSS на сервере) |
| `GET /api/news/sources` | список источников для фильтров |

Время в повторе — **offset (секунды от старта сессии)**; сервер переводит его в
абсолютную метку. Ручной `offset` во фронте — это подстройка второго экрана под
задержку эфира (FR-42).

Интерактивная документация: `http://localhost:8000/docs`.

## Соответствие функциональным требованиям (реализовано в каркасе)

- **FR-01..06 Timing Tower** — порядок, акроним/цвет команды, компаунд, последний
  круг; переключение интервал ↔ отставание от лидера; подсветка быстрейшего
  (фиолетовый) и личного лучшего (зелёный) круга; индикаторы DRS/PIT; выбор пилота кликом.
- **FR-10..15 Карты** — контур + старт/финиш; машины в реальном времени с цветом
  команды и подписями лидера/выбранного; зум колесом к курсору, панорама, сброс,
  индикатор масштаба; фильтр пилотов (Все/Никого/счётчик); **до 3 независимых карт**.
- **FR-20..23 Телеметрия** — активный пилот из таблицы или карты; мгновенные
  значения, бары газ/тормоз, скользящий график скорости; маппинг кода `drs`→open/closed.
- **FR-30..32 Стратегия шин** — шкала стинтов с цветом компаундов и маркером круга.
- **FR-40..43 Режимы** — повтор по `session_key` с паузой/скоростью (1/2/6/15×) и
  прогрессом; переключатель Live (нужен источник `openf1`); ручной offset; выбор сессии.
- **FR-50..51 Шапка** — круг/всего, статус-флаг из `/race_control`, погода.

### Разделы «Сезон» и «Новости»
Экраны вне живой гонки — три вкладки в шапке: **Гонка · Сезон · Новости**.

- **Сезон** (ТЗ §2.2) — источник [Jolpica-F1](https://api.jolpi.ca) (преемник Ergast):
  прогресс сезона, лидеры зачётов, обратный отсчёт до следующего этапа, бары
  личного зачёта и кубка конструкторов, доля очков по командам, календарь с
  таймлайном. Кэш 30 мин (зачёты меняются раз в уик-энд).
- **Новости** (ТЗ §10) — агрегация RSS **на сервере**: загрузка, разбор
  (feedparser), приведение к единой схеме, дедупликация по канонической ссылке
  (DR-N1) и по заголовку (DR-N2), сортировка по свежести, кэш 10 мин. Источники
  русскоязычные (Google Новости, F1News.ru, Championat) — переводчик не нужен;
  англоязычные ленты заведены, но выключены (см. `app/news/sources.py`).

Почему на сервере, а не в браузере, как в прототипе: у браузера нет доступа к
чужим доменам без CORS, а публичные CORS-прокси нестабильны — это прямо
зафиксировано в ТЗ §10.1. Теперь фронтенду достаточно **одного запроса к своему
API**.

Правовое (§10.10): отдаются только заголовок, короткая выдержка и ссылка на
оригинал; полные тексты не републикуются, источник указан у каждого материала.

Если источник недоступен, экран показывает состояние ошибки с кнопкой повтора —
**выдуманные данные не подставляются**. Ленты, которые не ответили, называются
явно, чтобы неполная выдача не выглядела полной.

**NFR:** отрисовка карт/телеметрии на Canvas (перерисовка отдельно от тяжёлого
DOM); адаптив десктоп↔мобильный; видимый фокус, `prefers-reduced-motion`;
устойчивость к сбоям (последнее состояние + статус «данные задерживаются»);
только публичные данные, без видео/DRM.

```

## Источники данных и права
- **OpenF1** — публичный API тайминга и телеметрии (основной источник).
- **Контуры трасс** — набор `bacinger/f1-circuits` (GeoJSON, построен по данным
  OpenStreetMap, © OpenStreetMap contributors, ODbL). Данные **не хранятся в
  репозитории**: скрипт `fetch_circuits.py` скачивает их при сборке, поэтому
  чужой набор не перераспространяется (ТЗ L-02). Без каталога приложение
  работает, просто без запасной геометрии.
- Видеопотоки не используются ни в каком виде (ТЗ §1.3, NFR-06).
